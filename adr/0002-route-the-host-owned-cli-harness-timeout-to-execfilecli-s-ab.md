# ADR-0002: Route the host-owned CLI harness timeout to execFileCli's absolute `timeout`

**Status:** Accepted
**Context:** test/run-architect-outcome.test.ts:285-329 drives every CLI harness adapter (claude, codex, opencode, pi) with `--timeout-ms 50` against a fixture that is silent for 500ms, and requires the rejection to match /timed out after 50ms/. Only the absolute-ceiling path carries that wording; the idle path deliberately says `produced no output for …`.
**Decision:** For each CLI harness adapter reached by runArchitect (the claude/codex/opencode/pi adapters under packages/baro-orchestrator/src/harness/**), the host-owned per-call timeout (the value behind `--timeout-ms`) MUST be passed to execFileCli/execFileCliBuffer as the `timeout` option (absolute ceiling), producing the ADR-001 message with `${options.timeout}` equal to that value. Do not introduce an adapter-local timeout message, do not wrap or re-word the execFileCli error on the way out, and do not remove any `idleTimeoutMs` the adapter already passes. If an adapter currently maps the host timeout only to `idleTimeoutMs`, add the `timeout` mapping rather than repurposing the idle option. Exactly one code path per adapter may set `timeout`; no other module may re-format the rejection for this test to pass.
**Consequences:** A host-owned timeout is now a hard ceiling for every CLI adapter regardless of CPU state, consistent with verify.ts:1053-1054. Agents must not 'fix' run-architect-outcome.test.ts by editing the test or the fake harness; the fixture at test/run-architect-outcome.test.ts:737-761 stays as-is.
