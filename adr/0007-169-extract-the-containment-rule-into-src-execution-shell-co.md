# ADR-0007: #169: extract the containment rule into src/execution/shell-containment.ts and materialize it into the Claude hook by source serialization

**Status:** Accepted
**Context:** bashContainmentRejection (codebase-tools.ts:1349) and its whole private graph (tokenizeShell:1907, rejectPathOperand:1579, hasMacosWriteSandbox:1809, isEnvironmentAssignment:1903, ShellAccessContext:994, shellAccessContext:1000, OpaqueInterpreter:1638, ShellToken:1337) live in the planning adapter and have exactly one caller (:937). The Claude hook is a generated standalone ESM file in a per-story directory; it cannot import orchestrator modules, because in development the orchestrator runs as TypeScript under tsx and in production it is a tsup bundle with no separate module files. The file already solves this for the publish guard by inlining `publishCommandRefusal.toString()` with a `__name` shim (hook-bridge.ts:65-66), which is the one convention that works in both modes.
**Decision:** Create packages/baro-orchestrator/src/execution/shell-containment.ts as the single owner. Move (do not copy) bashContainmentRejection and its entire private helper graph out of codebase-tools.ts into it, exporting:
  export interface ShellAccessContext { /* unchanged fields */ }
  export function shellAccessContext(...): ShellAccessContext   // signature unchanged
  export function shellContainmentRefusal(cwd: string, command: string, access: ShellAccessContext): string | null   // the former bashContainmentRejection, body unchanged
  export function shellContainmentHookSource(): string
codebase-tools.ts imports shellContainmentRefusal and shellAccessContext from "../../execution/shell-containment.js" and its line-937 call site is the only change there; native-lane behaviour, messages and message wording are byte-identical.
shellContainmentHookSource() builds the hook-inlinable JS by joining `fn.toString()` of the real functions (plus every module-level const/regex they read, emitted as `const <name> = ...` declarations, plus `import path from "node:path"` and `import fs from "node:fs"` and the `__name = (fn) => fn` shim). It must not hand-write a second implementation of the rule.
hook-bridge.ts: HOOK_SCRIPT's `pre-bash` branch interpolates `${shellContainmentHookSource()}` and, after the existing publishCommandRefusal check returns null, computes `shellContainmentRefusal(worktreeRoot, command, access)` where worktreeRoot and the access context come from a new `containment.json` written beside surface.json by writeHookSettings (fields: { worktreeRoot: string, collabCommand: string, collabCapability: string, scratchDir: ".baro-scratch" }); a missing or unparseable containment.json exits 0 like every other hook failure path. A refusal takes the existing path unchanged: append {command, reason} to GUARD_REFUSALS_FILE and print {decision:"block", hookSpecificOutput:{hookEventName:"PreToolUse", permissionDecision:"deny", permissionDecisionReason: reason}}. Both materializeStoryHooks and materializePublishGuardHooks install it, so a story with no declared write surface is contained too.
Refusals reaching ClaudeStoryAgent.drainCommandRefusals (harness/claude/story-agent.ts:589-601) emit the existing StoryCommandRefused with harness:"claude"; no new event type.
**Consequences:** One rule object, two enforcement sites. Every function moved into shell-containment.ts must stay free of module-scope imports it does not also emit into the hook source, so a future edit that reaches for a new import must extend shellContainmentHookSource() in the same commit. hasMacosWriteSandbox runs inside the hook process, so a non-macOS agent host gets the conservative branch exactly as the native lane does. A unit test must eval the generated source and assert it rejects `mktemp -d && git worktree add`, which is what keeps the two sites from drifting.
