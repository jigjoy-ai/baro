# ADR-0001: Extend TransientRetryOptions with fallbackWaitMs and an injectable sleep; change nothing else in withTransientRetry

**Status:** Accepted
**Context:** The dialogue policy must grow waits into the 60–120s range while keeping the provider retry-after as the base and the existing cap semantics, and the new tests must not sleep real minutes (today's tests really sleep, transient-retry.ts:69). Rejected: a parallel retry helper (violates the reuse constraint); changing the 3**(attempt-1) growth or the default 5_000 base in place (would silently change run-architect.ts, architect-openai.ts and model-participant.ts, an explicit non-goal); fake timers in the test (t.mock.timers would also have to cover unrelated code paths).
**Decision:** In packages/baro-orchestrator/src/harness/transient-retry.ts add exactly two optional fields to TransientRetryOptions and nothing else:
- `fallbackWaitMs?: number` — base wait used only when the classified failure carries no retryAfterMs. Applied as `const base = failure?.retryAfterMs ?? options.fallbackWaitMs ?? 5_000` and then `const waitMs = Math.min(base * 3 ** (attempt - 1), options.maxWaitMs ?? 30_000)`. Provider retry-after still wins as the base; the cap still applies to the whole product.
- `sleep?: (ms: number) => Promise<void>` — defaults to the current `(ms) => new Promise((resolve) => setTimeout(resolve, ms))`; line :69 becomes `await sleep(waitMs)`.
Do NOT change: the default maxAttempts (2), the classification/fail-closed block (:46-56), the `retryable?.(error) === false` veto semantics, the notice string format `attempt N failed (kind): msg; retrying in Xms`, or the default maxWaitMs (30_000). Do NOT add an AbortSignal, a jitter term, or a per-attempt callback.
**Consequences:** All existing callers keep byte-identical behavior because both fields default to today's values. New tests can assert the exact wait sequence in milliseconds without real sleeping by injecting a recording `sleep`. Because the sleep is not abort-aware, a turn deadline elapsing mid-wait is still only observed after the wait; acceptable since the conversation controller budget (turnTimeoutMs default 30 min) far exceeds the new maximum total sleep (~3 min per contract attempt).
