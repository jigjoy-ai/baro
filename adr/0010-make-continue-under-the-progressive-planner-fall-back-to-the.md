# ADR-0010: Make --continue under the progressive planner fall back to the complete-plan barrier instead of aborting

**Status:** Accepted
**Context:** main.rs:3975-3980 aborts with 'progressive planning v1 supports fresh runs only' whenever begin_progressive_execution is entered on a non-fresh run; --continue is by design a re-planning mode and has a working complete-plan path.
**Decision:** In main.rs, replace the hard error at :3975-3980 with a fallback: when the run is a continuation (BARO_CONTINUE / app.is_followup / cli.continue_run) or a resume, do not abort — print one line to the stream/log exactly `progressive planning is unavailable for continued runs; falling back to the complete-plan barrier` and take the existing complete-plan path (the same path used when --progressive-planning is not requested, i.e. build_command must not push `--progressive-planning`, orchestrator_client.rs:448-512). Add `fn progressive_mode_for_launch(is_fresh: bool, progressive_requested: bool) -> ProgressiveMode` (enum { Progressive, CompletePlanFallback }) as a pure function in main.rs with inline tests over all four input combinations. The abort remains only for the impossible case where the complete plan is missing, with an unchanged message.
**Consequences:** --continue keeps re-planning semantics; only the planner transport changes. Fresh runs keep progressive planning byte-for-byte. begin_progressive_execution's BARO_RUN_ID re-stamping at main.rs:3983-3994 must still run in the fallback path if that path spawns the executor.
